# ADR-003: Zero-dependency boundary, v0 public-signature restraint, and the pgtype/Optional split

## Context and problem

`functional` is meant to be freely adoptable by any other module in this
workspace, including modules other library modules (`postgres`, `eventbus`,
`workopher`) depend on. Three related risks had to be settled together
before other modules started importing it: whether `functional` itself
could accumulate dependencies over time, whether a *library* module (as
opposed to application code) should be free to put `functional` types in
its own exported signatures while `functional` is still pre-1.0, and — with
`postgres/pgtype` already shipping nullable value types generated by
`sqlc-gen-postgres` — where the line falls between that persistence
representation and `optional.Optional[T]` as a domain representation.

## Decision drivers

- `functional` must stay trivially auditable and safe to adopt: zero
  dependencies outside the standard library, forever, not just at v0.1.0.
- Go's Minimal Version Selection (MVS) resolves one version per module in
  the whole build; two consumers of the same v0 module pinned to different
  minors can fail to build together, and a v0 module's minor releases are
  explicitly allowed to break compatibility (unlike v1+).
- A library module's exported signature is a much larger liability surface
  than application code's: application code can be fixed the moment it
  breaks, but a published library module's signature is depended upon by
  consumers this workspace does not control the release cadence of.
- `sqlc-gen-postgres` already generates `postgres/pgtype.X` values with a
  `Valid bool` field for nullability — that representation exists and is
  correct for its layer; `functional` must not blur where that layer ends
  and domain code begins.

## Options considered

### Option 1: No dependency or signature restraint — treat functional like any v1 module

**Cons:** A `functional` v0.2.0 that changes `Optional[T]`'s shape would
silently break every library module that put `Optional[T]` in an exported
function signature, with no version bump on the library module itself to
signal the break; MVS could also select incompatible minors for two
consumers.

### Option 2: Require v1.0.0 for functional before anyone in the workspace may import it

**Cons:** Blocks real adoption and real-usage feedback for an unbounded
period; the fastest way to a good v1.0.0 API is exactly the usage this
option forbids.

### Option 3: Zero-dependency forever (tested), restrained to application code in exported library signatures pre-v1, explicit pgtype/Optional boundary (chosen)

**Pros:** `functional` can be adopted immediately by application code and
by library-module internals, with the actual compatibility risk (an
exported signature of a *published* library module) deferred until the API
has proven itself; the persistence/domain boundary is drawn once and
mechanically enforced at the one place it actually matters (the adapter).
**Cons:** Requires discipline from every library module's authors until
`functional` reaches v1.0.0 — there is no compiler enforcement of "don't put
this in your exported signature," only review and documentation.

## Decision

**Chosen: Option 3**, with three related sub-decisions:

**1. Zero-dependency, permanently, tested.** `functional` depends on
nothing outside the standard library — not "for now," permanently. This is
enforced by `functional/internal/archtest`
(`TestNoNonStdlibDependencies`, `TestPublicDependencyDAG`,
`TestGoModHasNoRequirements`), which fails the build the moment a stray
dependency creeps in, rather than relying on doc comments or review alone.

ADR-007 narrows the public-sibling rule for the nested values family: the only
permitted production edge is `functional/values/validated` →
`functional/values/nonempty`. Every other public-sibling edge remains forbidden,
and the permanent no-external-dependency rule is unchanged.

**2. Pre-v1.0.0, no library module puts `optional.Optional[T]` in its own
exported signature.** Until `functional` reaches v1.0.0, a library module in
this workspace (`postgres`, `eventbus`, `workopher`, and any future sibling)
must not expose `optional.Optional[T]` in an exported function, method, or
struct field — only application code may. Two reasons converge on this
rule: under MVS, two consumers of a v0 module pinned to different minors can
fail to build together the moment their build graphs meet, which is a much
sharper failure than a v1 module's guaranteed backward compatibility would
produce; and a breaking change to `functional`'s v0 API (permitted at any
minor, by semver's own v0 rules) would break the exported signature of an
already-published library module with no version signal of its own to warn
consumers. Application code carries neither risk in the same way: it is not
itself a dependency other modules resolve through MVS, and it can be fixed
in place the moment `functional` changes underneath it.

**3. `postgres/pgtype.X.Valid` is a persistence representation;
`optional.Optional[T]` is a domain representation; the conversion happens in
the adapter.** Generated code from `sqlc-gen-postgres` emits
`postgres/pgtype` value types (e.g. a `Text` with a `Valid bool` field) for
nullable columns — that is correct and unchanged by this ADR. Generated code
never emits `optional.Optional[T]`, and never will: that boundary stays with
the adapter layer that already sits between generated queries and domain
code, which is exactly where a `pgtype.X` → `optional.Optional[T]`
conversion (or the reverse) belongs. This keeps rule 2 satisfiable in
practice — `postgres` and `sqlc-gen-postgres` do not need `Optional[T]` in
their own exported surface, because the conversion is application-owned by
construction, not merely by convention.

## Consequences

**Positive:** `functional` can be adopted immediately, workspace-wide,
without waiting for v1.0.0; the actual compatibility hazard (a published
library module's exported signature) is deferred until the API has
real-usage evidence behind it; `postgres`'s generated-code boundary
(`adr:postgres:001`, `adr:postgres:002`) stays exactly as documented, with
no new coupling to `functional`.

**Negative:** Rule 2 is a review-time, documentation-level restraint, not a
compiler-enforced one — nothing currently fails a build if a library module
violates it before `functional` reaches v1.0.0; catching a violation depends
on the same review discipline this workspace already relies on elsewhere.

**Neutral:** This ADR does not commit to a v1.0.0 timeline; the module
README documents "two independent adopters" as the informal signal that
the API is ready to be promised stable.
